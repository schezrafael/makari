# M1.3 — Administración del catálogo

La sección **Catálogo** permite consultar bebidas activas e inactivas, crear bebidas,
editar sus nombres, agregar variantes con presentación en ml, editar variantes,
activar/desactivar y guardar precios Visitor/Local. Reutiliza AppShell, wordmark,
isotipo, botones y tokens Makari. No hay eliminación, inventario ni recetas.

## Contrato administrativo

| Método | Ruta | Cuerpo |
| --- | --- | --- |
| GET | `/api/products` | — |
| POST | `/api/products` | `{name, category}` |
| PUT | `/api/products/{id}` | `{name, isActive, version}` |
| POST | `/api/products/{id}/variants` | `{name, sizeMl, visitorPrice, localPrice, version}` |
| PUT | `/api/products/{id}/variants/{variantId}` | `{name, sizeMl, isActive, version}` |
| PUT | `/api/products/{id}/variants/{variantId}/prices` | `{visitorPrice, localPrice, version}` |

GET devuelve un arreglo de `{id, name, category, isActive, version, variants}`.
Cada variante contiene `{id, name, sizeMl, isActive, visitorPrice, localPrice}`;
precios faltantes de datos antiguos aparecen como `null`. Las escrituras devuelven
el producto completo con su versión vigente (`201` al crear, `200` al actualizar).
La categoría se captura al crear la bebida. Activar/desactivar es parte de PUT.

- Nombres/categoría: obligatorios, recortados, máximo 100 caracteres.
- Presentación: entero positivo en ml.
- Importes: `decimal(12,2)`, entre 0 y 9999999999.99, sin redondeo silencioso.
- Local no puede superar Visitor: el flujo existente lo interpreta como descuento.
- Nombre de bebida único sin distinguir mayúsculas; nombre y ml de variante únicos
  dentro de la bebida, incluyendo inactivos. Los registros existentes no se renombraron.
- `400`: validación; `404`: producto/variante inexistente; `409`: `catalog_changed`,
  `duplicate_product` o `duplicate_variant`. Identificadores mal formados no coinciden
  con las rutas GUID. Una versión omitida nunca autoriza una actualización.

`version` pertenece al producto completo. Cualquier cambio, incluidos precios y
variantes, la renueva. La interfaz conserva el formulario ante errores y ofrece
recargar, descartándolo explícitamente, para revisar el dato vigente. No sobrescribe
silenciosamente la edición concurrente. Los precios Visitor/Local se guardan juntos.

Las escrituras usan una transacción y un advisory lock exclusivo de catálogo en
PostgreSQL; las ventas adquieren el lock compartido antes de leer precios hasta el
commit. Esto ordena una venta concurrente respecto de una desactivación o cambio de
precio. EF también comprueba el token de concurrencia. La comprobación de duplicados
está protegida entre escritores administrativos; el SQL externo debe respetar el
protocolo. No se agregaron índices de nombres que pudieran fallar con datos existentes.

## Integridad comercial y migración

`GET /api/catalog` conserva su contrato y filtrado de productos/variantes activos.
Los endpoints administrativos no escriben en SaleItem ni recalculan ventas históricas.
Se mantienen expectedTotal, price_changed, claves de idempotencia y cierres de caja.
Una venta rechazada requiere nueva confirmación y clave; reintentar una venta ya
confirmada devuelve el comprobante persistido incluso después de cambiar el catálogo.

Migración generada: `20261105053626_ManageCatalog` (no aplicada).
Agrega `Products.Version` y cambia los checks de precios, subtotales y totales para
admitir cero. No actualiza importes ni precios existentes. Los productos antiguos
empiezan con versión GUID cero y reciben una nueva en su primera edición.
La validación y recuperación de checkout también admiten total cero.
El downgrade puede fallar si ya existen importes cero; no debe alterar historia para
forzar una reversión.

Antes de ejecutar esta versión, aplicar manualmente las migraciones en el destino
autorizado. No usar `makari_dev` sin autorización. No se migra ni siembra al arrancar.
Para revisar SQL sin aplicar cambios:

```sh
dotnet ef migrations script 20261105050434_SimplifyCustomerIdentification 20261105053626_ManageCatalog --project src/Makari.Api --output /tmp/makari-m13.sql
```

No mezclar nodos API anteriores y nuevos durante el despliegue: los anteriores no
participan en el bloqueo de catálogo. El proyecto sigue sin autenticación/roles;
las rutas administrativas deben permanecer en el mismo entorno de acceso controlado
que el POS. La lista carga todo el catálogo; paginación/búsqueda queda para catálogos
más grandes.

## Probar desde la interfaz

1. En una base autorizada con la migración aplicada y conexión configurada por
   variables de entorno/secretos locales, iniciar la API:
   `dotnet run --project src/Makari.Api --launch-profile http`.
2. Ejecutar `npm --prefix src/makari-web run dev` y abrir `http://localhost:5173`.
3. Abrir **Catálogo → Nueva bebida**, escribir nombre y categoría y guardar.
4. Pulsar **Agregar variante**, completar nombre, ml y ambos precios, y guardar.
5. Usar **Editar bebida**, **Editar variante** o **Editar precios**. Desmarcar
   **Activa** para desactivar; guardar confirma y vuelve a consultar la lista.
6. Volver a **Nueva venta**: se consulta de nuevo el catálogo vendible. Comprobar que
   una variante inactiva no aparece y que las nuevas cotizaciones usan el precio nuevo.
7. Abrir el mismo producto en dos pestañas: guardar en una y luego en la otra debe
   mostrar un conflicto. Recargar y revisar antes de volver a guardar.
8. Para comprobar recuperación, dejar una venta pendiente de confirmación, cambiar
   su precio desde otra pestaña y confirmar la venta: debe exigir revisar el total
   vigente y confirmar con una nueva clave, conservando el comprobante histórico.

## Verificación

```sh
dotnet build MakariPOS.slnx --no-restore
dotnet test MakariPOS.slnx --no-build
npm --prefix src/makari-web run build
npm --prefix src/makari-web run lint
npm --prefix src/makari-web test
```

Pruebas PostgreSQL opt-in: preparar manualmente **makari_test** con la última
migración, definir `MAKARI_TEST_CONNECTION` mediante secretos locales y ejecutar:

```sh
dotnet test MakariPOS.slnx --filter FullyQualifiedName~PostgreSqlCatalogManagementTests
```

La prueba rechaza cualquier otro nombre de base, comprueba que no haya migraciones
pendientes, enfrenta actualizaciones y creaciones duplicadas concurrentes y limpia
solo sus datos. No crea la base ni aplica migraciones. Sin variable se omite.

Resultado de esta implementación: build .NET sin advertencias ni errores; 152 pruebas
backend aprobadas y 7 PostgreSQL opt-in omitidas; build y lint frontend correctos,
52 pruebas frontend aprobadas. No se conectó a makari_dev ni se realizaron commits.
