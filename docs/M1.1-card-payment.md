# M1.1 — Tarjeta

Se admite `Cash=0`, `Transfer=1` y `Card=2`. PostgreSQL almacena PaymentMethod como
`integer`, con CHECK para los tres valores. Los precios y las reglas de idempotencia,
expectedTotal y confirmación de cierre permanecen iguales.

## Contratos HTTP

- `POST /api/sales`: `paymentMethod` admite `"Card"`, además de `"Cash"` y `"Transfer"`.
  La respuesta 201 (o 200 en reintento) devuelve el mismo método. Los demás campos
  de solicitud/respuesta no cambian; se mantienen `idempotencyKey`, `expectedTotal` e `items`.
- `GET /api/sales/summary?date=YYYY-MM-DD`: añade `cardRevenue` decimal. Conserva
  `date`, `timeZoneId`, `totalRevenue`, `cashRevenue`, `transferRevenue`, `salesCount`,
  `unitsSold` y `variants`. Total = efectivo + transferencia + tarjeta.
- `POST /api/cash-closes`, `GET /api/cash-closes?date=YYYY-MM-DD` y
  `GET /api/cash-closes/{id}`: sus respuestas añaden `cardSales` decimal.
  La solicitud de cierre no cambia. `expectedCash = openingCash + cashSales` y
  `totalRevenue = cashSales + transferSales + cardSales`.

Los cierres confirmados se leen de su snapshot: nunca se recalculan desde ventas.
Los históricos reciben CardSales=0 sin alterar TotalRevenue, ExpectedCash, Difference
ni otros importes. Los comprobantes antiguos del navegador también se restauran con cero.

## Migración manual en makari_test

`20261105002201_AddCardPaymentMethod` añade `DailyCashCloses.CardSales numeric(28,2)
NOT NULL DEFAULT 0` y amplía `CK_Sales_PaymentMethod_Valid` a `(0, 1, 2)`.
No modifica filas de ventas, precios ni importes anteriores del cierre.

1. Configurar localmente `MAKARI_TEST_CONNECTION` con una cadena Npgsql cuyo campo
   `Database` sea exactamente `makari_test`. No guardar credenciales en Git.
2. Generar y revisar SQL desde la raíz:

```sh
dotnet ef migrations script 20261027035313_AddDailyCashCloses 20261105002201_AddCardPaymentMethod --project src/Makari.Api --output /tmp/makari-card.sql
```

3. Aplicar explícitamente, solo después de comprobar el destino de la variable:

```sh
dotnet ef database update 20261105002201_AddCardPaymentMethod --project src/Makari.Api --connection "$MAKARI_TEST_CONNECTION"
dotnet ef migrations list --project src/Makari.Api --connection "$MAKARI_TEST_CONNECTION"
```

Para una base nueva, `database update` también aplica las migraciones previas.
La aplicación y las pruebas no aplican migraciones automáticamente.
No ejecutar estos comandos contra makari_dev. El rollback exige no tener ventas Card:
la restricción anterior rechaza el valor 2 y la reversión elimina CardSales.

## Prueba PostgreSQL opt-in

Con el esquema actualizado, ejecutar en una base makari_test de uso exclusivo durante
la prueba y con el día operativo actual abierto:

```sh
dotnet test MakariPOS.slnx --filter FullyQualifiedName~CardSale_IsPersistedReplayedAndIncludedInSummaryAndClose
```

La prueba rechaza cualquier nombre de base distinto de makari_test y cualquier migración
pendiente. Crea una venta Card por HTTP, reinicia el host, recupera la misma venta con la
misma clave, consulta resumen y confirma cierre. Verifica tarjeta, ingresos y efectivo
esperado, y elimina únicamente sus registros por IDs/claves en `finally`.
Sin MAKARI_TEST_CONNECTION queda omitida. No se ejecutó contra PostgreSQL en esta entrega.

- `dotnet build MakariPOS.slnx --no-restore`: sin errores ni advertencias.
- `dotnet test MakariPOS.slnx --no-build`: 129 correctas, 5 PostgreSQL opt-in omitidas, 0 fallidas.
- `npm --prefix src/makari-web run build`: correcto.
- `npm --prefix src/makari-web run lint`: correcto.
- `npm --prefix src/makari-web test`: 41 pruebas correctas.

Las pruebas cubren Card, idempotencia y expectedTotal, métodos desconocidos, resumen con
los tres métodos, efectivo esperado, snapshot histórico sin CardSales, SQL sin UPDATE,
selección visual, restauración de borrador, POST pendiente, confirmación y presentación.
