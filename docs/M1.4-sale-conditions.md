# M1.4 — Clasificación del comprador y condición de venta

## Modelo y reglas

`Customers.CustomerType` identifica al comprador: Visitor (1) o Local (0).
Todos los compradores existentes y los nuevos comienzan como Visitor, incluidos
los registros genéricos `visitante` y `local`. No se deduce la clasificación del
username, de sus ventas ni del botón usado para seleccionarlo. La actualización
explícita puede hacerse desde Nueva venta, consultando al comprador y pulsando
**Clasificar como Local/Visitor**. Esto no cambia la condición del pedido.

`Sales.SaleCondition` expresa una única condición por operación:

| Condición | Valor persistido | Precio cobrado |
| --- | --- | --- |
| Normal | 0 | Visitor |
| LocalDiscount | 1 | Local |
| Courtesy | 2 | 0 |
| Staff | 3 | 0 |
| Birthday | 4 | 0 |

Normal es el valor por defecto del contrato nuevo y de cada pedido nuevo en la UI.
Birthday es una cortesía manual, sin fecha de nacimiento ni elegibilidad.
`Sales.PaymentMethod` ahora admite null. El contrato nuevo exige null para todo
importe cero, incluso un precio Normal/LocalDiscount configurado en cero. Con
importe positivo exige Cash, Transfer o Card. Las condiciones gratuitas no son
métodos de pago.

`Sales.CustomerType` se conserva como **selector histórico de tarifa**, no como
clasificación del comprador. No se ha cambiado su significado; para operaciones
nuevas es una proyección de compatibilidad: LocalDiscount→Local, resto→Visitor.
La fuente de clasificación es exclusivamente Customers.CustomerType.
`Sales.CustomerId` sigue nullable para filas históricas sin comprador; el flujo de
registro sigue resolviendo un comprador para cada operación nueva.

`SaleItems.ReferenceUnitPrice` guarda el precio Visitor de referencia para nuevas
operaciones del contrato M1.4. UnitPrice/Subtotal siguen representando lo cobrado.
El descuento por renglón es ReferenceUnitPrice × Quantity − Subtotal. En registros
históricos la referencia y el descuento son null: no se inventan valores a partir
del catálogo actual.

## Contratos HTTP

### Cotización

`POST /api/sales/quote`

```json
{
  "saleCondition": "Courtesy",
  "items": [{ "productVariantId": "<uuid>", "quantity": 2 }]
}
```

La respuesta conserva `subtotal`, `discount`, `total`, `items` y añade
`saleCondition` y `unitsConsumed`. Cada renglón mantiene `visitorUnitPrice` como
referencia, `unitPrice` cobrado y sus importes. Para dos bebidas con referencia 60:
subtotal=120, discount=120, total=0, unitsConsumed=2. QuoteSale y el contrato nuevo
de CreateSale comparten la selección de precios; exigen variantes/productos activos,
referencia Visitor disponible y, para LocalDiscount, precio Local válido que no
supere Visitor. El comprador no participa en el cálculo.

### Registro

`POST /api/sales`

```json
{
  "idempotencyKey": "<uuid>",
  "customerUsername": "ana",
  "saleCondition": "Courtesy",
  "paymentMethod": null,
  "expectedTotal": 0,
  "items": [{ "productVariantId": "<uuid>", "quantity": 2 }]
}
```

Se puede usar customerId de un comprador conocido en lugar de customerUsername;
no ambos. Omitir ambos conserva el comprador genérico visitante. El frontend
mantiene la identificación por username. Omitir saleCondition y el campo legado
customerType selecciona Normal. No enviar customerType en clientes nuevos.

La respuesta añade saleCondition y, en cada item, referenceUnitPrice y discount.
PaymentMethod puede ser null. Se mantienen 201 para creación y 200 para reintento,
400 para validación y 409 con price_changed, idempotency_conflict o daily_cash_closed.
El servidor vuelve a calcular importes; expectedTotal sigue siendo obligatorio.
Una variación del precio de referencia de una cortesía no cambia el total cero;
el registro guarda la referencia vigente al confirmar.

### Clasificación del comprador

- `GET /api/customers/frequent?limit=5`: añade customerType a cada comprador.
- `GET /api/customers?username=ana`: consulta exacta normalizada; 200 con
  `{id, username, customerType}`, 404 si aún no existe, 400 si el username es inválido.
- `PUT /api/customers/{id}/classification` con
  `{ "customerType": "Local", "expectedCustomerType": "Visitor" }`:
  204 al actualizar; 409 customer_changed si ya cambió la clasificación; 404 si no
  existe. La comparación y escritura son una única sentencia SQL. La UI permite
  consultar nuevamente ante conflicto. No se crea el comprador desde este endpoint.

### Resumen y cierre

`GET /api/sales/summary` añade:

- `unitsRegistered`: todas las unidades; `unitsSold` se conserva como alias legado.
- `paidUnits`: unidades con UnitPrice > 0.
- `freeUnits`: unidades con UnitPrice = 0, incluidas tarifas cero de Normal/LocalDiscount.
- `conditions`: cinco entradas `{saleCondition, operations, units, revenue}`,
  distinguiendo cortesías, Staff y cumpleaños incluso sin movimiento monetario.

Los ingresos se calculan con importes persistidos, nunca con el precio de referencia.
El cierre conserva su contrato: CashSales, TransferSales, CardSales, ExpectedCash,
CountedCash y Difference. Las operaciones gratuitas incrementan registros/unidades,
pero no los ingresos ni el efectivo esperado. Los cierres confirmados no se recalculan.

## Idempotencia y recuperación

Las solicitudes antiguas que contienen customerType y no saleCondition conservan
el algoritmo original de fingerprint, tarifas y validación compatible. Visitor se
interpreta como Normal y Local como LocalDiscount. Esto también conserva el caso
legado de total cero con método de pago; las solicitudes nuevas no lo permiten.

Las solicitudes nuevas usan una huella `v2` que incluye condición, pago (o ausencia),
variantes/cantidades y la identidad enviada. Cambiar Courtesy por Staff con la misma
clave produce conflicto aunque ambas tengan total cero. RejectedSaleAttempts conserva
sus datos y la terminalidad de cada clave; no se recalculan sus fingerprints.
Reintentar una venta confirmada devuelve sus importes históricos, incluso después
de cambiar el catálogo, la clasificación del comprador o cerrar caja.

El almacenamiento de checkout sigue siendo `makari.checkout.v1`. Se admiten borradores,
comprobantes y solicitudes antiguas. Un borrador antiguo sin intento mantiene la
intención localDiscount al mostrarse como LocalDiscount; un pedido nuevo empieza
Normal. Las solicitudes pendientes antiguas se reenvían sin agregar saleCondition.
Las nuevas guardan la condición antes del POST y la reenvían sin modificaciones tras
un timeout. Cambiar comprador o condición está bloqueado mientras haya un intento
pendiente. La comparación entre borrador e intento detecta alteraciones de condición.
Un rechazo terminal permite revisar el borrador y confirmar con una nueva clave.

## Migración y plan de datos históricos

Generada, **no aplicada**:
`20261105230915_CustomerClassificationAndSaleConditions`.

1. Hace nullable PaymentMethod, sin cambiar sus valores históricos.
2. Agrega SaleCondition y ejecuta únicamente esta reclasificación de Sales:
   `CASE CustomerType WHEN 0 THEN 1 ELSE 0 END` (Local→LocalDiscount, Visitor→Normal).
3. Agrega ReferenceUnitPrice nullable sin rellenarlo con precios actuales.
4. Agrega Customers.CustomerType con default Visitor para todos, sin inferencias.
5. Agrega checks para valores de condición y operaciones gratuitas con total cero y
   sin pago. Conserva Sales.CustomerType, fingerprints, importes, intentos y cierres.

El downgrade se bloquea si existen condiciones gratuitas o pagos null. No transforma
operaciones gratuitas en efectivo. Aun si el guard permite revertir, se perderían los
campos nuevos de clasificación/referencia; preferir corregir hacia adelante.

Plan manual de despliegue:

1. Respaldar y revisar el SQL sobre una copia autorizada; contrastar conteos por tarifa,
   sumas históricas, fingerprints y cierres antes/después.
2. Detener nodos API antiguos y aplicar la migración explícitamente en el destino
   autorizado. No usar makari_dev sin autorización.
3. Desplegar backend nuevo antes del frontend nuevo; conservar el adaptador legado
   para recuperar solicitudes guardadas. No alternar nodos backend viejos y nuevos.
4. Verificar Normal/LocalDiscount, cada condición gratuita, resumen, cierre y reintentos.

Para generar SQL de revisión sin aplicarlo:

```sh
dotnet ef migrations script 20261105053626_ManageCatalog 20261105230915_CustomerClassificationAndSaleConditions --project src/Makari.Api --output /tmp/makari-m14.sql
```

Riesgos de compatibilidad:

- Clientes que asumían PaymentMethod obligatorio deben admitir null.
- El campo customerType de respuestas de venta/cotización sigue siendo legado, no
  clasificación; clientes nuevos deben usar saleCondition y consultar Customers.
- El adaptador legado se identifica por customerType explícito. El frontend antiguo
  siempre lo persistía; integraciones externas que omitieran ese campo deben revisarse.
- Un frontend antiguo no puede editar condiciones nuevas ni restaurar sus solicitudes;
  evitar volver a una versión anterior con intentos M1.4 pendientes.
- Los usernames `local`/`visitante` no garantizan clasificación. Clasificar explícitamente
  los compradores que corresponda; no hay actualización automática por nombre.
- El esquema actual del POS sigue sin autenticación/roles administrativos. La nueva
  actualización de clasificación requiere el mismo control de acceso del entorno.

## Interfaz y prueba manual

Con la migración aplicada manualmente en una base autorizada:

```sh
dotnet run --project src/Makari.Api --launch-profile http
npm --prefix src/makari-web run dev
```

Abrir http://localhost:5173. En Nueva venta:

1. Escribir username o seleccionar V/L/frecuente. Consultar la clasificación o salir del
   input para consultarla; cambiarla explícitamente si procede. Verificar que siga Normal.
2. Agregar bebidas, elegir una de las cinco condiciones y revisar la cotización.
3. En cortesía/Staff/cumpleaños, verificar descuento completo y ausencia de pago.
4. Confirmar. Revisar unidades y condiciones en Ventas del día y montos en Cierre de caja.
5. Simular una respuesta de red incierta y recargar: recuperar la misma operación con
   la misma condición/clave, sin volver a cobrar ni cambiar el borrador pendiente.

Se reutilizan la navegación, wordmark/isotipo y los componentes/tokens Makari existentes.
No se agregaron puntos, recompensas, cumpleaños de clientes, inventario ni pagos mixtos.

## Verificación

```sh
dotnet build MakariPOS.slnx --no-restore
dotnet test MakariPOS.slnx --no-build
npm --prefix src/makari-web run build
npm --prefix src/makari-web run lint
npm --prefix src/makari-web test
```

Resultado: 161 pruebas backend aprobadas, 8 PostgreSQL opt-in omitidas; 59 pruebas
frontend aprobadas. Build .NET y frontend correctos; lint sin advertencias.
La prueba de migración valida el esquema y ejecuta su sentencia real de reclasificación
sobre filas aisladas SQLite, preservando importes/pagos/fingerprints. No se ha aplicado
la migración sobre una base real ni se certifica todavía la ejecución PostgreSQL.

Opt-in PostgreSQL: preparar manualmente makari_test con la última migración y la fecha
comercial actual abierta. Definir MAKARI_TEST_CONNECTION mediante secretos locales:

```sh
dotnet test MakariPOS.slnx --filter FullyQualifiedName~PostgreSqlSaleConditionTests
```

La prueba rechaza otros nombres de base. Comprueba condiciones concurrentes con una
misma clave, actualización concurrente de clasificación, recuperación desde otro host
y traducción de agregados PostgreSQL. Limpia solo sus datos; no crea bases, no aplica
migraciones y no altera cierres. Ejecutar las pruebas PostgreSQL aisladamente, pues
otras suites opt-in pueden cerrar la fecha comercial de makari_test.
