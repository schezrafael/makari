# M1.2 — Identificación sencilla de compradores

El comprador es independiente del operador (`RegisteredBy`) y del tipo de precio
(`CustomerType`). No hay buscador, registro previo, pantalla CRUD ni autenticación.

## Flujo

- Nueva venta: input Comprador vacío, chip V seleccionado y comprador `visitante`.
- V asigna `visitante`, vacía el input y activa precio Visitante.
- L asigna `local`, vacía el input y activa precio Local.
- Escribir o seleccionar un frecuente rellena el input y conserva el tipo de precio.
- Vaciar el input vuelve a Visitante. Descuento local sigue siendo independiente.
- El comprador se reutiliza o crea al confirmar, dentro de la transacción de la venta.
- Tras confirmar una venta, se restablece el input vacío y Visitante.
- Los frecuentes se consultan una vez al montar la pantalla, nunca por tecla.
  Si fallan, todavía se puede escribir y vender. Se muestran hasta cinco usernames
  reales, sin inventar chips cuando hay menos compradores con ventas.

El borrador conserva el texto y la selección genérica. La solicitud completa, incluido
`customerUsername`, se persiste antes del POST. Mientras el resultado sea incierto,
no se puede editar el comprador ni los demás datos. La recarga reutiliza exactamente
esa solicitud y su idempotencyKey.

No se recibió una captura de referencia: la interfaz sigue la estructura textual solicitada,
con tokens Makari, input de ancho completo y chips que se ajustan en varias filas en móvil.

## Normalización

Se eliminan espacios extremos y se compactan espacios repetidos. Se admiten de 1 a 40
caracteres normalizados: letras ASCII, números, espacios internos, punto, guion y guion
bajo; el primero debe ser letra o número. Entrada máxima: 256 caracteres.

La unicidad usa la columna calculada PostgreSQL `lower("Username")` y un índice único.
La API normaliza los espacios antes de persistir. `Ana  Luna`, ` ANA LUNA ` y `ana luna`
reutilizan el mismo Id. El primer registro conserva sus mayúsculas.
Los nombres reservados actuales son `visitante` y `local`; V/L son etiquetas de chips.

## Contratos HTTP

### POST /api/sales

```json
{
  "idempotencyKey": "<guid>",
  "customerType": "Visitor",
  "paymentMethod": "Card",
  "customerUsername": "Ana Luna",
  "expectedTotal": 60,
  "items": [{"productVariantId": "<guid>", "quantity": 1}]
}
```

`customerUsername` es opcional. Ausente, null o vacío asigna `visitante` a una venta nueva.
La interfaz envía explícitamente `visitante`, `local` o el username escrito normalizado.
El precio siempre depende de CustomerType y de QuoteSale, no del nombre del comprador.

201 confirma una venta nueva; 200 recupera la ya confirmada. La respuesta conserva todos
los campos anteriores, incluyendo `customerId` y `customerUsernameSnapshot`. Estos dos
siguen siendo null al recuperar una venta histórica que no tenía comprador.

El username normalizado sin distinguir mayúsculas forma parte de la huella de idempotencia.
Cambiarlo bajo la misma clave produce `409 idempotency_conflict`. Se conservan ExpectedTotal,
RejectedSaleAttempts, los métodos de pago y el bloqueo tras el cierre.

Compatibilidad: se conserva `customerId` únicamente para solicitudes pendientes del contrato
anterior; no se permite combinarlo con customerUsername. Las solicitudes antiguas sin identidad
conservan su huella original para recuperar ventas/rechazos existentes. No se reescriben
intentos guardados ni snapshots históricos. Los borradores antiguos seleccionados por Id
siguen siendo legibles y pasan al flujo de username al iniciar una solicitud nueva.

Un username inválido produce 400. La creación de compradores ocurre después de validar cierre,
productos y total. PostgreSQL usa `INSERT ... ON CONFLICT DO NOTHING` y relee el comprador
existente dentro de la misma transacción. Si falla guardar la venta, se revierte también el
nuevo comprador. Los rechazos no crean compradores huérfanos.

### GET /api/customers/frequent?limit=5

Devuelve un array de `{ "id": "<guid>", "username": "Ana Luna" }`.
Limit predeterminado 5; se admiten 1–5, otros valores devuelven 400.

Orden: cantidad de ventas descendente, compra más reciente descendente y username normalizado
para un empate completo. Excluye `visitante`, `local`, los IDs genéricos históricos y ventas
sin CustomerId. Solo consulta Sales; los rechazos no participan. PostgreSQL agrega y limita
los resultados en SQL.

Se retiraron GET /api/customers?username=... y POST /api/customers. No hay creación separada.

## Migraciones

Se conserva `20261105040101_AddCustomers`: tabla, índice único, relación nullable y snapshot.
Se añade `20261105050434_SimplifyCustomerIdentification`, que cambia los genéricos anteriores
v/L a visitante/local sin modificar ventas, precios ni snapshots.

Si ya existe un comprador con el nombre reservado de destino, se reutiliza para ventas nuevas
y se conserva el antiguo genérico y sus relaciones históricas. No se fusionan IDs ni se
eliminan compradores. Los IDs genéricos anteriores también se excluyen de frecuentes.
La reversión intenta restaurar v/L; puede fallar si esos nombres ya fueron registrados después.

No se aplicó ninguna migración y no se modificó makari_dev.

## Verificación PostgreSQL opt-in

Configurar localmente `MAKARI_TEST_CONNECTION` con una cadena Npgsql cuyo Database sea
exactamente `makari_test`. No guardar credenciales en Git. Desde la raíz:

```sh
dotnet ef migrations script 20261105002201_AddCardPaymentMethod 20261105050434_SimplifyCustomerIdentification --project src/Makari.Api --output /tmp/makari-customers.sql
```

Revisar el SQL y comprobar el destino de la variable antes de aplicar explícitamente:

```sh
dotnet ef database update 20261105050434_SimplifyCustomerIdentification --project src/Makari.Api --connection "$MAKARI_TEST_CONNECTION"
dotnet ef migrations list --project src/Makari.Api --connection "$MAKARI_TEST_CONNECTION"
```

Con el día operativo actual abierto, sin otros procesos escribiendo durante la prueba:

```sh
dotnet test MakariPOS.slnx --filter FullyQualifiedName~PostgreSqlCustomerTests
```

La prueba rechaza bases distintas de makari_test y esquemas con migraciones pendientes.
Crea dos ventas concurrentes con el mismo username y diferente casing/espacios; exige
un solo comprador, verifica que un rechazo no cree otro, consulta frecuentes y recupera
una venta tras reiniciar el host. También verifica conflicto al cambiar de comprador.
Limpia únicamente sus filas mediante claves/IDs aleatorios. Nunca aplica migraciones.
Sin MAKARI_TEST_CONNECTION se omite; no se ejecutó contra PostgreSQL en esta entrega.

Verificación manual adicional: registrar sin username, con L y con un nombre nuevo;
confirmar que la nueva venta vuelve a V. Repetir el POST con la misma clave y consultar
frecuentes; debe haber una sola venta para esa clave. Probar un ExpectedTotal incorrecto
con otro nombre y verificar que no existe ese comprador.
